### 1. 「include 選到東西」的定義

ADR 020 原本的定義是「比對到過一個走得到、沒被排除的節點」，比對到的當下就記。審查找到兩種比對到卻
什麼都沒還原、也沒有警告的情況：

- `--include X --include '!X'`：X 比對到了，但被後面的 `!X` 取消。
- `--include <root 的上層> --exclude <root>`：上層在沿 root 定位走的時候比對到，但 root 被排除了。

新定義：一條正向樣式比對到某個被還原的節點或它的上層，才算選到東西。實作上每個位置帶著「比對到自己
或上層、還沒記過的正向樣式」，節點被還原時才一起記。被還原的節點包括 `visit` 回傳的、被選到的位置，以及
被選到的落點（空的目錄 root 也算）。

考慮過只記「決定選取的那一條」（最後比對到的樣式），沒採用。同一個節點被幾條樣式比對到時，沒決定的
那條會被誤報成沒選到，例如 `<某個檔案> *.pdf`，或 `<root 的上層> <root>`。新測試的對照釘住這兩種。

還原有錯誤時（例如某個目錄建不起來），那個目錄底下沒有走到，所以「沒選到」可能不完整。CLI 的警告這時
改說「在走到的項目裡沒有比對」，不說成 snapshot 裡沒有。目錄建不起來就放棄它的內容，這是原本就要的行為，
沒有改。

### 2. 清單與樣式檔的讀法

ADR 024 寫「名稱與切法同 restic」，審查拿 restic 0.19.1 對同一批檔案實跑，發現不同。現在的規則：

- 兩種文字清單（`--files-from`、`--files-from-verbatim`）與所有樣式檔：開頭的 UTF-8 BOM 去掉，以 `\n`
  切行，行尾的一個 `\r` 去掉。verbatim 也去 `\r`，同 restic 的 bufio.ScanLines。
- `--files-from` 與樣式檔去掉前後空白，用 Unicode 的空白，同 restic 的 TrimSpace。不成 UTF-8 的行只去
  ASCII 空白。原本清單只去 ASCII、樣式檔去 Unicode，兩者不一致。
- `--files-from-raw`：每個名字都要以 NUL 結尾、不能是空的，否則結束碼 1，同 restic。
- `-` 是標準輸入，樣式檔也可以用。整個命令只能給一次，清單與樣式檔合計；原本第二個默默讀到空的。restic
  也是讀到空的。
- include 樣式檔一條樣式都沒有時是錯誤，restic 沒有這條檢查。照讀的話 include 是空的，等於整份還原，審查
  時實際覆寫了目標裡改過的檔。exclude 的空樣式檔照常。

刻意與 restic 不同的地方：

- 標準輸入也去 BOM。restic 只對具名檔案去，從標準輸入讀時 BOM 會留在第一個路徑上。
- UTF-16 清單不支援（restic 會轉碼）。它會因為找不到路徑或不是 UTF-8 而失敗，不會默默少備。

## 延到 v4（需要改格式）

- **V19：檔案來源的判別有歧義。** 目錄 root `x/foo` 恰好只含一個檔案 `foo` 時，會被當成檔案來源，還原成
  `x/foo` 這個檔案。`restore latest:<…>/x/foo` 也回「不是目錄」。main 也一樣，是 v3 的映射規則本身的問題。
  `docs/format.md` §9 原本寫「結果相同、沒有歧義代價」，這是錯的，已更正。v4 在 root 記種類，不再猜。
- **V21：每個 root 一個 tree。** `--files-from` 列 2000 個檔案就是 2000 個 root，各自一個 tree 物件與
  `.r1` 副本。實測 10.96 s，同樣的檔案放在一個目錄裡是 0.16 s；20 000 個是 162 s 對 0.89 s。strace 下
  8017 次 fsync 佔 14.2 s 裡的 11.1 s。來源規劃的平方迴圈已在 `b5e25f6` 修掉，剩下的成本來自格式。ADR 017
  的 trees-in-packs（v4）把 tree 放進 pack，不再一個 tree 一個物件。

## 沒修（記錄在這裡）

- **V22a：不分大小寫時字面與字元類別不一致。** `ß`、`ſ`、`İ`、Kelvin 符號在字面比對與 `[...]` 裡的
  結果不同：字面比的是整串小寫，類別逐字元試大小寫。只影響這幾個特殊字元，沒有改。
- **V22b：Windows 風格的樣式。** `AppData\Local\Temp` 的 `\` 是跳脫字元，整條變成一個字面段，比對不到
  任何東西也不報錯。Windows 的路徑語意屬於 PLAN「已接受的限制」，沒有 Windows 環境，不在 Linux 上猜。
- **V23a：真的還原與 dry run 兩條走訪的重複。** 落點與記帳已共用（`place_roots`、`open_placement`、
  `Select`）。逐節點的兩條走訪是 ADR 022 刻意的結構，靠一致性測試把關。
- **V23d：樣式編譯兩次。** CLI 為了點名出處先逐行編譯一次，排程工作每次也重新編譯。成本小，沒有改。
- **V13：遠端來源的記號探測。** 個別項目錯誤與同名的檔案、目錄碰撞，方向都是安全的（多備，不是少備）。
- **補掃：遠端來源的記號探測重新列目錄。** 走訪自己的列表還在記憶體裡時又列一次，巨大的遠端目錄峰值
  記憶體會加倍。沒量測（UNVERIFIED），沒有改。
- **補掃：`one_file_system_keeps_mount_points_empty` 在沒有 user namespace 的環境印「skipping」後照樣
  通過。** 在受限的 CI runner 上它是綠的但什麼都沒測。Rust 的測試不能在執行時標成略過，所以留著，記在
  這裡。

## 駁回

- **V24c：** 加寫入權之後沒有提早結束的路徑。`ensure()` 回傳的是已經開著的 handle。
- **V25：** restore 重用 backup 的排除樣式檔時，不錨定的 `tmp` 會排掉路徑經過 `tmp` 的整個 root。這是
  ADR 020 記下的取捨，README 寫明：restore 的樣式也比對 root 與它的上層。
- **V22c：** `start()` 不設 decision，只是潛在問題：沒有呼叫端在起點狀態上讀它。

## 後果

- 結束碼：只有 `!` 的 include、沒有樣式的 include 樣式檔、`-` 給兩次、raw 清單格式錯誤、root 落點在
  更深處建不起來，都改成 1（原本是 0 或 3）。
- 訊息：沒選到東西的警告是 `include pattern "X" selected nothing: …`，不再點名 `--include`。設定檔的
  記號錯誤改成 `[backup] exclude marker "…": …`。
- API：`Exclusions::new`；`unmatched_includes` 的定義改了，型別沒變。
- 測試：每一項都有先紅後綠的測試。V11 與 V20 只在 Windows 編得到，沒有 Windows 執行環境，是 UNVERIFIED：
  windows-gnu cross clippy 只做型別檢查，並以放進一個型別錯誤確認它真的有編到。
