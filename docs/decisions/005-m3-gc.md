# ADR 005：M3 —— 無鎖 GC（forget / prune / repack）

日期：2026-09-05。狀態：已採用。

## 背景

PLAN 要的是 Duplicacy 式的無鎖兩階段 GC：標記 → grace → 刪，任何 client 引用到被標記的東西就復活；
inactive client 不阻擋；repack；以及「刻意競態下永遠不會刪到活的 chunk」。
格式在 M1 凍結，M3 只新增了 `gc/` 標記的內容定義（固定 magic），沒有動任何既有結構。

## 決定

### 1. 標記不帶內容，時間用後端的修改時間

`gc/<hex>` 的內容固定 8 bytes。原本考慮加密的 `GcMark{target, kind, marked_at, marked_by}`
（需要新的 ObjectKind），但 prune 每次都從 snapshot 重算活物件，標記裡的資訊沒有任何決定依賴它；
唯一需要的「何時標記」後端本來就記（本機 mtime、S3 LastModified，M2 的 probe 與 S3 測試都驗過
重 put 會刷新、conditional put 失敗不會刷新）。少一個格式結構、少一個要 key 才能讀的東西。
偽造標記的人（有寫入權限）最多讓垃圾早一點被刪，刪不到活的東西。

### 2. backup 不刪標記，改成「不拿被標記的 pack 去重」

PLAN 寫「backup 引用到被標記的 pack 就刪除標記」，但那需要 Delete 權限，違反 Put-only。
改成 backup 開始時列 `gc/`、被標記的 pack 視同不存在（chunk 重寫）；標記後才引用到的情況
（backup 開始得比標記早）由 prune 第二階段重算引用時撤銷。效果相同，backup 仍然 Put-only。

### 3. 活的 pack 不挑正本

同一 chunk 在兩個 pack 都有時，兩個 pack 都算活。挑正本會讓「哪個 index 版本在解析」變成
安全性的一部分；不挑就對任何讀取端都安全，代價是重複的空間 v1 不回收（寫進 format.md §11.5）。

### 4. 刪 pack 前先重寫 index；孤兒 pack 不重寫

advisor 抓到草案的洞：只刪 pack 不改 index，下一次 backup 會對不存在的 pack 去重、check 會報錯。
現在任何在 index 裡的 pack 被刪之前，都先寫一個不含它的 blob（supersedes 全部）。
不在 index 裡的孤兒刪掉不需要重寫（不然每刪一個孤兒就多一輪 blob 更替，GC 永遠不收斂）。

### 5. commit 前逐 chunk 驗證，而不是逐 pack

proptest 找到的 bug：repack 只搬「有 snapshot 引用」的 chunk，進行中的 backup 去重到的 chunk
在 prune 眼裡是死的，會從 index 消失；舊 pack 還在（孤兒、等 grace），逐 pack 的 HEAD 檢查看不出來，
snapshot 寫出後指到 index 裡沒有的 chunk，下一輪 GC 就把它刪了。
修法：commit 前重新載入 index，這次引用的每個 chunk 都要解析得到、pack 存在、標記沒過期；
否則安全失敗，重跑會重傳。另外 repack 不碰比 grace 年輕的 pack（進行中 backup 自己的 pack
永遠不會害自己失敗）。代價：backup 結束時多一次 index 載入（有快取時只讀新 blob）與每個引用的
pack 一次 HEAD；`referenced` 要在記憶體裡放這次所有 chunk id（每個 32 bytes，100 萬 chunk ≈ 60 MiB），
M5 的記憶體目標要把它算進去。

### 6. 寫過的 tree 也在 commit 前檢查

tree 每次 backup 都重 put，修改時間會刷新；prune 刪前會再 HEAD 一次，看到比標記新就撤銷。
所以只有「put 發生在標記之前」（backup 跑超過 grace）才危險：commit 前對有過期標記的已寫 tree
比較修改時間，沒比標記新就失敗。正常情況這個集合是空的，零成本。

### 6b. 跑超過 grace 的 backup 直接拒絕 commit

200 案例的 proptest 找到第二個洞：backup 跑超過 grace，它寫的 tree 被標記、刪掉、標記也清了，
commit 時的檢查（§5、§6）什麼都看不到，snapshot 指到不存在的 tree。逐 tree HEAD 太貴
（一個 tree 一次），所以改成執行「grace 必須長於最長 backup」這條合約本身：
commit 時 `now - started >= grace` 就以 `BackupTooLong` 失敗。重跑會沿用已上傳的 pack（去重）與
parent 的快速路徑，通常很快；真的每次都超過就該把兩邊的 grace 調高。

### 7. 同一 client id 一次一個 backup：檔案鎖

「活躍 client 在標記後有新 snapshot」假設每台 client 的 backup 是序列的。排程重疊會破壞它，
所以 CLI 在 client id 檔旁邊上 `client-id.lock`（std 的 `File::try_lock`，程序結束自動釋放），
第二個 backup 直接失敗。

### 8. grace / inactive 是 CLI 參數，不進 config

backup 這邊不再依賴 inactive 門檻（每台都做同樣的檢查），只有 grace 兩邊要一致
（`backup --gc-grace` 與 `prune --grace`，預設都 72 h）。不一致的後果只在 backup 跑超過 grace 時
出現，而且是安全失敗那一邊。

### 9. forget 立即刪 snapshot

snapshot 是 commit point，沒有人會「引用」它（parent 只在 backup 開始時讀一次）。
保留政策照 restic：last / hourly / daily / weekly / monthly / yearly / within，以 (client id, paths) 分組。

### 10. 競態測試

- 確定性測試：標記→grace→刪的時間線（注入時間）、復活、inactive 不阻擋、引用不完整拒絕、
  年輕物件不標、dry-run、pack 消失時 commit 安全失敗、重載 index 找到搬走的 chunk、
  過期標記、repack 丟掉 chunk 時 commit 安全失敗。
- proptest（`tests/gc_race.rs`）：兩台 client 的 backup（拆 prepare / commit）、forget、prune、
  時鐘推進的隨機交錯；每一步之後 `check --read-data` 無錯誤、commit 只能成功或安全失敗、
  最後每個 snapshot 還原出來等於當初的內容。24 個案例進 `cargo test`，`PROPTEST_CASES=200` 跑過。
  時鐘是注入的：測試骨架把每一步新寫出的物件 mtime 蓋成注入時鐘，物件年齡與 snapshot 時間才在
  同一條時間軸上（第一版骨架混用真實 mtime 與注入時鐘，製造出不合邏輯的案例）。

## 沒做（留給之後）

- 重複 chunk 的空間回收（§3）。
- 免 List 的 backup 模式（Put-only 定義仍含 List）。
- S3 Object Lock 的實際測試（只處理刪除失敗：回報、保留標記、結束碼 3）。
- 記住寫過的 tree 以省掉每次 backup 的 tree put（ADR 003 的承諾，M2 也沒做）。
- `referenced` 的記憶體（§5）與快取合併的串流化（ADR 004）一起在 M5 處理。
